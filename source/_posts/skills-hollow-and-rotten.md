> 我丢过去一句，我的技能库有点缺失，估计是备份的时候还原出了错，我重新从云端拉了一份备份，你看看有没有 skill 能对上的。
>
> 它数了一遍，回来告诉我：一个都没少。
>
> 三十七个目录，按名字逐个对，全在。只是它们全是空的。

## 一、坏的是一批目录，不是一批技能

“缺失”这个词用错了，而且错得挺关键。

磁盘上三十七个技能目录，三十个能正常加载，坏掉的是八个。坏法还各不相同：

| 技能 | 剩下什么 |
|---|---|
| EvidenceFirst | 一个空的 `references/` |
| GitHubOps | 一个完全空的目录 |
| HumanizerZh | 空壳，`scripts/` 里的脚本没了 |
| ProbeIntent | 空壳，只剩 `scripts/` |
| SelfImprovingAgent | 空壳，`memory/`、`references/`、`templates/` 全空 |
| SeoOps | 空壳，`references/` 底下十二个内容子目录，全是空树 |
| HtmlDesign | 六十四个文件都在，**只缺入口 `SKILL.md`** |
| MidiGeneration | 磁盘上连目录都没有 |

前六个是“名字还在，内容没了”。这是最阴的一种坏法：技能列表里它们照样出现，路由照样会把请求派过去，派过去才发现那边是空的。装得像没事一样。

最后一个不一样，它是当年被主动删掉的，不在这一批里。

## 二、四份备份，是同一个坏掉的时刻

我丢过去的那份备份在 `F:\Downloads\claude-portable.zip`，三百四十兆。它另外又找出三份：

| 副本 | 尺寸 | 位置 |
|---|---|---|
| 云端拉回来的 | 340 MB | `F:\Downloads\claude-portable.zip` |
| 还原产物 | 500 MB | `Resources\claude-portable-2.1.233-restored.zip` |
| 解包现场 | 已解包 | `Temp\cc-restore\claude-portable` |
| 回收站里那份 | 340 MB | 与第一份同尺寸同时刻 |

四份，全是同一个受损状态。那七个技能在四份里全是零文件的空壳，`EvidenceFirst`、`GitHubOps`、`SeoOps` 三个在云端那份里连目录都没有。按技能名逐个对完，这份备份能提供的净增量是**零**。

更扎心的是那份备份的来历：它是**另一台机器**上完整可用的便携包，U 盘部署、H 盘、用户名“纳指GO”。它曾经真的是一份好备份，只是不是这台机器的。

那它怎么坏的？时间戳给出了答案。

`EvidenceFirst`、`GitHubOps`、`SeoOps` 三个目录的时间戳停在当天 **17:15:02**。`HumanizerZh`、`ProbeIntent`、`SelfImprovingAgent`、`HtmlDesign` 停在 **17:53:00.000**，毫秒是整整齐齐的三个零。

毫秒为整，是“按备份里的时间戳写回”留下的指纹，那是解压还原的典型特征。

于是事情连起来了：17:53 那次还原，**只写了目录骨架，没把文件写进去**。然后云端把这份已经坏掉的状态备份走了。我 18:58 再把它拉回来，拉回的就是同一个坏掉的时刻。

所以“还原出了错”这个判断是对的，只是得补一刀：**备份没有说谎，它忠实地记下了坏掉的那一刻。** 问题不在于备份不可信，在于备份的**时序**让它变成了事故的一部分。

## 三、动手之前，先核一份“已删勿恢复”名单

技能库的恢复有个反常识的地方：**恢复这个动作本身是有破坏性的。**

我有条自己定的规矩，记在它的记忆里，叫“已删勿恢复”。它记的是那些**我确认删掉、以后也不许复活**的技能。一份完整的旧备份摆在那儿，看起来是救命稻草，实际上里面躺着好几个已经被判过死刑的东西。手一快恢复了技能库，顺手也就把它们带回来了。

名单上三个：`MidiGeneration`（磁盘上连目录都没有的那个）、`SeoOps`（十二个空目录那个）、`EvidenceFirst`。它们的目录后来都删干净了，引用也清了。

这条规矩真正管用的地方，是把“恢复”从一个纯技术动作变成一个**需要先考证的动作**。备份不是真相，备份只是某个时刻的快照。

清完这一轮，剩下的账目是：

| 类别 | 数量 | 说明 |
|---|---|---|
| 保留空壳 | 4 | 路由悬挂，最危险 |
| 部分损坏 | 1 | HtmlDesign |
| 已确认废弃 | 3 | 目录已删、引用已清 |
| 空目录但无引用 | 3 | 历史遗留，无害 |
| 健康技能 | 31 | `SKILL.md` 引用的文件路径逐条实测，零断链 |

那三十一个的健康是实测出来的，不是估的。每条 `SKILL.md` 里写着的文件路径挨个去磁盘上验，一条断链都没有。这数字后来很有用：它证明了这次损坏是**局部的**，没烂到根上。

## 四、八个文件名对上了同一个上游

八个里最难办的是 `ProbeIntent`。它只剩一个空的 `scripts/`，别的一无所有。

最顺手的做法是照着损坏清单把它写回来。清单列得很清楚：它应该有 `SKILL.md`、一个对照文档、五个脚本。按描述把八个文件写出来，一天就能交差。

这条路被否了。理由是：**那样产出的是一份看着完工的赝品。** 真正让这个技能好用的东西不在文件清单里，它有三百来行正文、三条路径分支、每一处都有批准关卡，还有一份规格自审协议。照着文件名写，这些全写不出来。外表像，骨头是假的，而且假得不容易被发现。

于是换了个问题。不问“这个技能该写什么”，问“**这个东西是不是已经存在于某处**”。

落点是八个文件名对上一个开源插件里的同名技能，**八比八全中**。真正让判定成立的不是数量，是两个不该撞的细节：两个 `.md` 放在技能**根目录**而不是 `references/` 子目录里；`.html` 模板却放在 `scripts/` 里。这种布局巧合的概率低到可以当指纹用。

身份一旦确定，事情就从“重写”变成了“取回加改造”。三条佐证：

**一、行号指纹。** 本机一条旧记录里写着，某个文件的第 132 行引用了一个已经断链的资源。上游同一句话在第 243 行。一百一十一行的偏移量说明两件事：本机这份是上游的**衍生品**，不是独立作品（所以取上游是对的）；而且它确实被本地删改过（所以要重放改造，不是原样拷回来）。

**二、从活着的邻居反推。** 技能本身死了，但别的技能还在引用它。追问纪律那份子文档描述了它的走访方式，规格自审那份描述了它的自审协议，路由表里还留着三条指向它的条目。**行为可以从引用者身上回收，即使产物本身没了。** 有点像用周边语言里的借词去复原一门死语言。

**三、用统计及时收手。** 调用记录里，上游那个同名技能被调过 **22 次**，而 `ProbeIntent` 这个名字是 **0 次**。这一条直接推出“改名之后再没被调用过”，于是“去历史会话里翻调用现场”整条路当场作废，省掉了对几十个记录文件的搜索。**知道哪里不必找，和知道哪里去找一样值钱。**

最后交付的东西里，每一句结论都标了等级：实锤、间接、推测。还专门列了一节“查不到的部分”，六项，写明白是不知道，而不是用想象填平。

那是“重建”和“编造”之间的那条线。

## 五、唯一没丢文件的那个，是屎山

八个里伤得最轻的是 `HtmlDesign`。

它六十四个文件一个没少，只缺一个入口文件，补上就能加载。从损坏清单的角度看，它是这一批里最好修的。

修复那天我顺手问了一个问题，这个技能的结构到底是清楚还是混乱。回答写在项目概览里：**五层结构，依赖单向，无环**。

骨架是干净的。层与层之间的依赖没有绕回来，没有环，这在这类资产型技能里算相当体面。

然后我把它判了死刑。

“屎山”这个词是我说的，说的不是它的目录结构，是它的**内容**。

最要命的一类问题有个准确的名字：**静默死路**。

有两份子文档，教你导出独立 HTML、教你交接给别的工具。它们依赖两个宿主提供的接口。而技能自己的说明文档里，白纸黑字写着这两个接口**本机没有替代品**。

问题在于，那两份文档没有任何抬头警示，而且还挂在活跃索引里，等着被推荐给你。你会从头读到尾，一路照做，然后在最后一步静默失败，没有报错，没有提示，就是没成。

更绝的是它的兜底方案。其中一份推荐的替代路径，正是另一份**缺了解码器**的文档。一处失效指向另一处失效，双重死路。

剩下的毛病排起来：两份文件正文 **95% 逐字相同**，一份是另一份的真子集，而它俩互相不引用；主脚本 68 KB，里面有四个空字节，导致 `grep` 把它当二进制文件跳过，**搜不到**；文档里写的是下划线文件名，磁盘上实名是连字符，三份文档受影响。

**结构的美救不了内容的烂。** 清晰和可用是两件事。一个依赖单向无环的技能，照样可以让你照着做完之后一场空。

于是决定不是修，是推倒重来。

## 六、重做之前，先定三条

重构最容易犯的错是把能跑的部分也一起重写了。所以第一个决定是**冻结管线**。

技能里那五个 `.mjs` 脚本是整个包里唯一实测能跑的部分，纯 node 直跑，不需要装依赖。它们当黑盒看待：接口写进规格，内部一行不动。屎山主要在文档层，那就只动文档层。

第二个决定是**砍掉转译层**。这个技能是双语的：中文的入口和路由，英文的子技能，中间还有一层“能力名到真实工具名”的映射表，因为它是从支持多个宿主的形态演化来的。问题在于我本机只用 Claude Code，另外两份映射是死重。而且前面那几类毛病，下划线文件名、上游工具名、抬头不齐，全部是这层转译带来的。砍掉，它们一起消失。

第三个决定是**按类重分组**。三十多份子技能原本按英文字母序排，没有分组，这才是“乱”的真正来源。重组成三块：制品形态、设计系统、导入与交接。重复的合并，设计系统那五份并成三份。

代价写清楚了：以后想换宿主，工具名得重写。认了。

## 七、五个字，“原子智能体”

计划出完是九个任务。摆在面前两条路，一是当前会话里逐个做，二是每个任务派一个全新的子智能体、任务之间评审。

我问选哪个。

回答是五个字：**原子智能体。**

意思是每个任务一个独立的智能体，互不共享上下文，做完交给另一个智能体评审，评审不过再派第三个复审。听上去是重活，但它解决的是真问题：同一个上下文里做完了自查，等于没查。

于是开工。九个任务，全程有明确的关卡：技能合规校验、引用完整性、差异保全。任务四是十五份互相独立的文件，并行跑。

那个会话里最后留下了 **87 条**智能体之间的往来消息。有交付、有评审结论、有打回重做、有复审通过。有一条评审把“关卡二是瞎的”这个问题摆到了台面上，它发现关卡脚本在仓库外，`git status` 永远干净，所以那个关卡其实什么都没守住。这类问题自己查自己查不出来。

## 八、跑了一个小时的那个

有一段时间，我盯着屏幕问了一句：你看一下子代理在干嘛，跑了一个小时了。

它在跑一个矩阵。**九十九个填充形态，乘以若干引用形态**，每个用例真起一次无头 Edge 浏览器，把渲染后的 DOM 拉回来比对。一次两三秒，几百次就是几十分钟。

进度是可量化的：九十九个形态的浏览器真相已经缓存在案，逐形态的探针行写到了一百一十二条，还剩九条没结论，大概九成。

为什么值得等：那里有个缺陷是**扫描器和浏览器结果不一致**。脚本说没问题，浏览器里是坏的。这种缺陷没有第二个裁判，只有真的把页面渲染出来才知道谁对。慢得有道理。

## 九、末态

重构之前，八十九个文件，四点一九兆。重构之后，五十四，四点零七兆。文件数掉了四成。

推公开仓那一次，提交是 `0801a04`，**七十七个文件，加 1124 行，减 3941 行**。

删掉的，是写进去的三倍多。

回头看，这一轮修的是两种完全不同的东西，用的也是两套完全相反的手法：

| | ProbeIntent | HtmlDesign |
|---|---|---|
| 坏法 | 八个文件全没，只剩空目录 | 六十四个文件俱在，只缺入口 |
| 顺手做法 | 照着清单重写一份 | 打个补丁修一修 |
| 实际做法 | 找到上游，**认领**回来 | 备份原文，**推倒**重做 |
| 判据 | 有源头，就别创作 | 是屎山，就别维护 |

伤得最轻的那个，是唯一被整个推倒的。
