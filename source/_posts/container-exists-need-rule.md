> 我丢过去一句，你知道 Claude Code 的当前文件夹在哪里吗。
>
> 它没直接答，先跑了一遍 `pwd`，又查了一遍配置根，然后把答案分成两半递回来。
>
> 我站在 `E:\WorkZone`，而它本体住在下面的 `ClaudeCode\` 里——自包含，不落 C 盘。

## 一、它不知道自己住在哪

这不是随口一问。

那阵子我在查另一件事：GitHub 的操作事实散在好几个地方，有的在记忆里，有的在文档里。查着查着发现我更该先弄清的是另一件——**这些东西到底存在磁盘的哪个位置**。

于是问题一路问下去：包在哪、配置根在哪、记忆目录在哪、GitHub 的事实落在哪几个文件里。

它一条条查完，给出的是一个自我包含的布局：会话工作目录是工作区根，Claude Code 本体和它的全部配置都在根下面那个 `ClaudeCode\` 目录里。`HOME` 被启动器重定向进去，`CLAUDE_CONFIG_DIR` 指进去，**整个包自带运行时，一个字节都不落 C 盘**。

这份布局后来长成了一个技能。当时的原话是：

> 不错，现在把当前零碎分散的 GitHub 事实移到这个技能的 `references` 里面，这样只用维护一个技能，避免漂移。

「只用维护一个技能，避免漂移」。这句话后来变成了上一篇里那个事实库。

## 二、工具库是给我自己用的

第二件事看着完全不相干。

`Tools\` 是我自己的目录，里面是 Aria2、Bandicam、BiliDownloader、CheatEngine、PotPlayer、Steam++、SillyTavern 这些日常用的 GUI 工具。

问题出在另一半：Agent 干活的时候，也会往里面塞东西。它写的脚本、它的包装器、它临时留下的辅助程序，全都落在同一个目录里。

我提了个方案：

> `tools` 文件夹都是我日常会用到的 GUI 工具，是面向我个人用的，但是在 Agent 使用过程中，Agent 经常会往里面塞一些在 Agent 里面会用到的工具。我想能不能通过在 Claude Code 里面建一个 `script` 文件夹，来管理这些 Agent 用的文件，避免我自己个人用的工具库污染，请你客观评定该方案的收益。

我特意加了「客观评定」四个字，因为我知道自己的直觉可能是错的。

## 三、你要的容器已经有了，缺的是规则

它拆了三层来看收益。结论里最硬的两句是：

> 文件夹是惰性的；起作用的是「`CLAUDE.md` 里写死一条正向规则 + 每次会话都能看到」。没有规则，`script/` 会变成第二个空目录。

> 收益不依赖新目录：写进工作区根的 `CLAUDE.md` 即可（每次会话必加载）。写到别处——包括包内、包括这个 `script/`——都不生效。

最后给的净评是：

> 建目录的收益接近零，把「禁令」改成「有地址的路由规则」的收益是主要部分且成本极低——你的直觉方向对（需要容器），但容器已经有了，缺的是规则。所以真实收益 = 规则收益（高）+ 新目录收益（≈0 或负，因引入歧义）。

新目录的收益是**负的**，理由是歧义：多一个名字相近的目录，以后每次都要多想一下东西该放哪。

我认了，并让它删掉我刚建的那个空文件夹。

于是真正落地的是一条**正向规则**，而不是一句「别乱放」：工具归谁管，按来源分，写清楚每一类该去哪里、新增之后要同步一份到哪里。这类规则在文档里看着平淡，但它和一句话禁令的区别是：禁令只会被读完之后忘掉，路由规则带着地址，读完就知道该走哪条路。

## 四、四跳的入口链

第三件事是启动。

那时候双击一个图标，背后要过四跳：

```
OpenClaude.cmd  →  ClaudeCode\tools\ensure-chain.cmd
                →  ClaudeCode\claude.cmd
                →  ClaudeCode\bin\claude-launch.cmd
                →  claude.exe
```

每一跳都干一点事：定位包、拉本地引擎、拉协议转换层、最后重定向 `HOME` 和 `PATH` 起本体。

这套设计本身没错，但它有个我受不了的性质：**如果一个地方断了，不好排查。** 双击的结果就是一个窗口一闪，或者干脆没反应。中间四跳里哪一跳没过去，信息全丢了。

我的要求很直白：集成成一个文件，顺便多埋一点点位。

它做出来的东西是今天的 `OpenClaude.cmd`，**10,613 字节，纯 ASCII**，四段全部在一个文件里：

```
1/4 bundle : 定位包
2/4 engine : 本地引擎（在端口上没答才起）
3/4 shim   : 协议转换层（不健康才起）
4/4 launch : 重定向 HOME / USERPROFILE / TEMP / PATH，起本体
```

每一段的路径都从**这个文件自身的位置**推导出来。它写在文件头的注释里：整个工作区可以整体改名、整个搬走，除了宿主 Node 那一条路径，这个文件一个字都不用改。

四跳合成一跳之后，被删掉的是 `claude.cmd`、`bin\claude-launch.cmd`、整个 `bin\`、以及 `tools\ensure-chain.cmd`——**四个文件走回收站**。

## 五、埋点：窗口关掉之后，日志是唯一残留证据

埋点是这次真正花心思的地方，因为「多埋一点点位」这句话底下藏着个约束：双击的窗口是会关掉的。

设计是这样的：

| 项 | 形态 |
|---|---|
| 每段一行 | 走 stderr，带等待秒数 |
| 同一份 | 追加落盘，日志文件固定位置 |
| 失败时 | 另打一个诊断块：`[FAIL]` 加段名、加退出码、加端口、加日志路径 |
| 可调 | 日志位置、跳过哪段、每段等多久，各有环境变量 |

最后那行诊断是关键。窗口关掉之后，日志是唯一残留的证据。**一个没有日志的失败，看上去和「这个程序本来就是坏的」没有区别**——这条在钩子那篇里出现过一次，这里是它的第二次。

验证走的是三个层次：诊断路径的输出和旧启动器逐行一致；`--version` 打出本体版本号；最后拿真实参数跑通整条链，确认退出码是 0，而且**协议通道没被污染**——那几行 `[chain]` 全在 stderr，`-p` 的 JSON 输出干净。

它顺手交代了一条只在这种场合才会出现的坑：`cmd.exe` 是按字节偏移续读批处理文件的，而这个文件当场被改写了。所以**起这个会话的那个窗口，退出时可能报一行错**。下次启动才是干净验证。

## 六、什么叫「跟着盘走」

做这件事的起因里，有一条比启动链更根本。

我说了一句打算：

> 我打算将 E 盘装到别的电脑上，比如说在别的电脑上显示 F 盘也可以用。

这块盘上装着整个工作区，包括 Claude Code 本体。它要被物理拔下来，插到另一台机器上，而新机器上的盘符可能是 F。

它先给了一个**负数**。我一度想把某个东西挪到 C 盘去、顺便改注册表，它的评价是：

> 收益是 -1：文件离开了会走的那块盘，而它需要在那里才能在新机器上被重新注册。

然后它把真正的问题点出来。文件在哪不重要，路径是相对的、都从自身位置推导，搬哪都对。**烧死在注册表里的那条绝对路径才是搬不动的那个。**

这里面最重的一项它单独拎出来说了：

> Claude Code 按路径给项目目录命名，你的全部持久记忆就在这个目录底下。

**记忆目录的名字是盘符加路径拼出来的。** 盘符变成 F，它会按新路径重新算一个键、新建一个目录，旧的记忆不会跟过去。

![](/img/360px/container-exists-need-rule-1.jpg)

而且这不是第一次。工作区那时候的迁移脚本里，映射表还留着上两代盘符的条目——这块盘之前从 H 盘、从 A 盘都迁过一次。这套痛苦是有历史的。

## 七、一条「始终遵守」的约束被降级了

约定不是只增不减的。

有一条全局约束是「所有文件必须 LF 行尾」，跟着我很久。后来我把它撤了：

> 这个行尾的坑可以废弃了，它实际上是 CI/CD 或者其他自动化构建的坑，可以直接塞到 GitHub 技能里面，不用再始终遵守。另外，在编写文档时不要防御性编写出现墓碑，写之后告诉我改了哪些文件就行。

这里面有两个动作。一个是**降级**：一条要时刻记着的全局约束，被降成某个技能里的一个坑。理由是它根本不属于全局——只有走 CI 或别的自动化构建时才咬人，日常写文件根本碰不到它。把只在 5% 场景生效的规则挂在 100% 的路径上，代价是每次都要为它花一点注意力。

另一个动作是顺手提的：**在文档里不要写墓碑，改完告诉我改了哪些文件就行。**

一句话里同时做了减法和加法。减掉一条全局约束，加上一条写作纪律。这两件事在同一个句子里出现，说明它们其实是同一件事的两面：**约束的数量是有配额的。**

## 八、一句话的偏好

这一组会话里还有一处，和工具、和约定都没关系。

它当时交上来一份很长的汇报，我回了一句：

> emm，你能用 AskUserQuestion 向我确认吗？一大段文字会让我注意力分散，这对你我都不好。

这不是脾气，是成本核算。长汇报在两端都要付钱：我读完要花注意力，而它写完还占着上下文；而如果那份汇报的实质只是「接下来做 A 还是做 B」，那么一个二选一的提问框比一千字的分析有用得多。

在这套环境里，**沟通形态也是要设计的东西**，和埋点、和日志、和路由规则一样。

它后来学会了。到这一组的后半段，很多时候不等我说，需要拍板的地方直接就抛一个选择框过来。

## 九、末态

这一组里做出来的东西，今天大多还在：

`OpenClaude.cmd` 还是那一个文件，10,636 字节，比当时多了二十来个字节。中间那四跳对应的文件，今天确实都不在了。

工具归属那条规则，今天写在工作区根的 `CLAUDE.md` 里，一共四行：临时文件放哪、大型工具链装在哪、工具归谁管、明文凭据不能放哪。全部是可执行的路由，没有一句禁令。

还有一条今天已经不在 `CLAUDE.md` 里了——就是那条被降级的行尾规则。

至于那个最重的担心，今天有了实测答案。

`projects\` 目录底下，**只剩一个键**：`E--WorkZone`。

工作区从 `work_zone` 改名成 `WorkZone` 之后，按路径算出来的那个键也跟着变了。旧键和它底下的会话记录已经不在这个目录里，清洗稿是它们唯一的副本；那批老记忆倒是留下来了，以一份归档的形式躺在 `Archive\Memories\` 下面。

不用等换机器、也不用等换盘符。**改个名字就够了。**

这一组的约定，绕来绕去都在回答同一个问题：**这条东西归谁管，断了从哪里看出来。**

前半句决定了它写在哪一层，后半句决定了出事时你能看见什么。文件夹、目录、编号本身都是惰性的，起作用的是那条被人每次都会看见的规则。

而路径里带着盘符的那一部分，是这套布局唯一没法彻底解决的地方。它只能被推迟。
