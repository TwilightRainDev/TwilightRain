> 我给的审计要求只有一句：**不要说“文档写得不好”**。
>
> 只要能被机器核对的句子。引用能不能解析到真文件，命名文件在磁盘上有没有，grep 有没有命中，脚本退出码是几。

它交回来一份报告，列了十二项结构问题，外加一节管线缺陷。我逐条看下来，发现这十二项有一个共同点，而且不是“严重”。

**是它们全都不报错。**

## 一、先把它说的每一句都变成能核对的东西

先摆清家底。这个技能包叫 `HtmlDesign`，产 Apple 风格的 HTML 制品：原型、幻灯片、文档、设计系统。它不是一个程序，是指令集加资产 —— Markdown 讲怎么做，`agents/` 里的 Node 脚本干机械活，`starter-components/` 给可以直接抄的起步代码。

重构前它的分层是这样的：一个入口，加四层子树。

| 层 | 规模 | 是什么 |
|---|---|---|
| `SKILL.md` | 1 份 | 路由：先定模式，再读设计层，再选形态，最后自检 |
| `apple/` | 8 份 | 设计语言层。规则、动效参数、两套模式规格、两套 token、交付清单 |
| `starter-components/` | 12 份 | 可以直接拷进项目的起步代码 |
| `built-in-skills/` | 33 份 | 子能力手册，其中 32 份是上游英文原文 |
| `references/` + `agents/` | 4 份 + 31 份 | 宿主映射与可执行管线（后者光 vendor 就占三点一兆） |

结构上它是干净的：五层，依赖单向，无环。

重构之前：八十九个文件，四点一九兆。

审计报告里我要求它标明证据。比如“交叉引用完整”这一条，它的证据是“三十三份子技能全部被 `SKILL.md` 提及，零孤儿文件；五个管线脚本各被二到八份文档引用”。这是可以复核的，我复核了，成立。

坏消息也照这个规矩写。后面每一节，我都尽量给出可复现的判据。你如果手上也有一个攒了两年的提示词包或者资产包，这些判据可以直接抄。

## 二、静默死路：索引在推荐一条走不通的路

最要命的一类毛病，报告给了它一个准确的名字：**静默死路**。

说的是有两份子文档，一份教你导出独立 HTML 单文件，一份教你交接给别的工具。它们各自依赖一个宿主提供的接口。而这个技能自己的说明文档里，白纸黑字写着：这两个接口**本机没有替代品**。

问题在于三点：

- 那两份子文档**没有任何抬头警示**；
- 它们还挂在 `SKILL.md` 的活跃索引里，等着被推荐；
- 走完它们依赖的接口之后，失败是**静默**的。没有报错，没有提示，就是没成。

整条路径的形态是：你会从头照做，一路顺利，然后在最后一步得到一片安静。

Tweaks 那一套更隐蔽。它由三个文件组成（`tweaks-panel.jsx` 加两份手册），面板的交互也都写全了。但它的三个 `postMessage` 接收方是 claude.ai 的托管宿主，本地起 HTTP 服务打开时 `window.parent === window`，没有接收方。也就是说，**该发消息的都发了，没人接**。而在整份宿主映射文档里，tweak 相关的内容零命中 —— 连“这个功能在本机不成立”这句话都没有人写过。

还有第四处，是我觉得最值得记的：它的兜底方案指向另一处失效。

那份不能用的导出文档，推荐的替代路径，正是另一份**缺了解码器**的文档。一处死路指向另一处死路。这是双重死路，而且写得像是给了你一条活路。

这类死路不是一个两个，是四个类别，全部指向同一个原因：技能是从“支持多个宿主”的形态演化来的，而有些能力只有某一个宿主有。

| 缺口 | 原因 | 后果 |
|---|---|---|
| PPTX 导出（2 份手册） | `agents/gen-pptx/` 缺 21 个源文件加 2 个构建产物 | 链路不可用 |
| 视频导出 | `agents/gen-video/` 缺全部 14 个文件加产物 | 链路不可用 |
| Figma 导入 | 缺一个 319 KB 的解码器，来源不可归属，已决定不恢复 | 脚本一跑必然 `ERR_MODULE_NOT_FOUND` |
| 六项宿主不成立 | 依赖那个网络产品的专有工具 | 已从索引移除，文档留着 |

:::admon[note]
判定这类问题的机械判据：把每一份子能力文档里提到的工具名抽出来，与“本机真实存在什么”逐条对照。工具名是有限集合，抽得干净就查得完。这一轮里被抽出来、又在本机找不到任何替代的，是六项。
:::

## 三、同一份依赖，入口说“活跃”，结尾说“不可用”

同一个依赖，在这份技能里得到了两个相反的判定。

`SKILL.md` 的索引表里，`save-as-standalone-html` 安安静静地挂在活跃清单上；而同一份文件的另一节，`send-to-canva` 因为依赖同样那两个工具，被判为不可用 —— 那一节的表头写着“本机不成立”，一共六项。

两边都对。它们只是没对账。

这类矛盾特别难自己发现，因为**人在读文档时是按节读的**。读索引表的时候你信索引表，读故障清单的时候你信故障清单，两份都是真的，矛盾只在把它们摆到一起时出现。

机械判据也很简单：拿同一个工具名，grep 整个技能树，看所有出现处给出的结论是否一致。这个方法我在自己写的审计清单里一直留着，现在是第二次救我一命。

值得记一笔的是那两处的距离：同一份文件里四十多行。索引表是后来整理的，故障清单是最早从上游抄下来的，两次写入之间隔了几周。**矛盾很少产生于某一次错误的编辑，通常是两次各自正确的编辑留下来的。** 这也是为什么对账必须交给机器做 —— 人不会在写索引表的时候，回头去读四十行以前那份故障清单。

## 四、一个 68 KB 的文件，对搜索是隐形的

这条我至今觉得最有教育意义。

那个技能最核心的构建脚本 `build-preview.mjs`，六十八 KB，一千九百多行，做的是把设计系统编译成一张自包含的预览页。它**能跑**，`node --check` 通过，实测输出逐字节稳定 —— 这后来成了整个重构里最有用的一条基线。

但它的文件里有**四个裸 NUL 字节**。

偏移量 10199、10226、10718、10724，落在第三百一十八到三百二十九行之间。看前后代码，本意应该是空格转义之类的东西，写成了真的零字节。

在 JavaScript 的字符串和正则字面量里，裸 NUL 是合法的。所以脚本能跑，语法检查能过，一切正常 —— 只有一个后果：

```
$ rg 'DS_CARD_RE' agents/build-preview.mjs
binary file matches (found "\0" byte around offset 10199)
```

它不输出内容行。`grep` 和 `ripgrep` 都把这个文件当二进制，跳过内容，只报一句“有个匹配”。要看得见，必须先加 `--text`。

**这意味着，这个技能包里最大、最核心的文件，对所有内容检索是隐形的。**

后果不是“搜不到某一处”，是更坏的那种：当你想找某个逻辑在哪、想确认某个常量有没有被引用、想改一处东西之前先看看谁在用 —— 你搜一遍，得到零命中，然后你相信了那个零。

这类东西没有任何间接症状。不会崩，不会变慢，不会报警告。只有字节级探针看得见它：读进来，`b"\x00" in data`。我后来把这一条写进了工作区的自查清单 —— 内容检索的可信度，和文件里有没有异常字节，是同一件事。

修法是四个字节换成转义序列。修完之后 `rg` 能正常输出内容行，这条也就成了重构验收标准里可机械核对的一条。改动的证明方式同样要机械：git diff 只允许出现那四处。

这里有个容易漏掉的细节：`node --check` 通过这件事，从头到尾没有鉴别力。它对裸 NUL 无感，对写错的变量名也无感，它只做语法解析。把“脚本能跑”当成健康证据，等于把体检做成“还喘着气”。所以那四个字节最后靠两条证据钉死：`rg` 从一句 `binary file matches` 变成能输出内容行，以及 diff 里恰好四行。

## 五、两份 95% 相同的文档，谁都不引用谁

`design-components.md` 和 `create-design-system.md` 这两份文档，正文约 95% 逐字相同。前者是后者的真子集。

它们互相不引用。

这一条在报告里排在重复问题里，但它的性质其实和陈旧的重复不太一样。95% 相同意味着：你改了 A，B 还是旧答案；你看到 B 照着做，A 里的新规则一点没进去。**两份文档会给你两个不同的答案**，而两个答案都长得像官方的。

同一份报告里还有一句更扎人的：`design-components.md` 的 description 里承诺了一个 `.dc.html` 的文件形态，而它的正文里，这个字符串**零命中**。承诺写在门口，屋里没有这个东西。

设计系统那五份文档里，还有三处在平行维护同一个契约。改一处忘两处是必然的，不是概率问题。

机械判据：取每两份文档做文本比对，重合度超过 50% 就是问题，不管它们是不是互相引用。修法是合并，不是加一句“另见 XX”。加交叉引用只是让你知道有两个答案，不会让你只剩一个答案。

五份设计系统文档最后并成了三份。合并的动作是取并集去重，不是各留一半 —— 三处平行维护的同一份契约只剩一处，另外两处变成对它的引用。并完之后，同一份磁盘格式终于只有一种说明。

## 六、下划线文件名，是转译层留下的指纹

`built-in-skills/` 那批英文手册里，命令是这么写的：

```
copy_starter_component(kind: "deck_stage.js")
```

而磁盘上的实名是 `deck-stage.js`，连字符。三份文档受影响，包括那份讲幻灯片制作的。

`copy_starter_component` 是上游宿主的工具，本机没有。本机有的是 `cp`。这类名字本来靠一层“宿主映射”转译过来 —— 技能包里专门有 `references/claude.md`、`cursor.md`、`codex.md` 三份，一份对应一个宿主。

问题在于这层转译**只覆盖了能力名，没覆盖字面文件名**。能力名转过去了（“复制起步组件”变成 `cp`），参数里的文件名原样留着，带着上游的下划线。你照着抄，命令在第一步就失败，而失败信息看起来像是“文件不存在”，不像“文档过期”。

这层映射的设计意图本身是合理的：能力名与真实工具解耦，换宿主只改一份映射。多宿主时代它是好东西。但在单宿主环境里，它剩下的唯一作用就是制造能在两处不一致的转译。**一个抽象层在它服务的对象只剩一个之后，就不再是抽象层，而是中间商。**

报告里给了这一层的量化：纯中文文档九份，纯英文三十六份，混排三份。语种分界就是这层接缝的形状 —— 中文那半是本地重写的入口与设计层，英文那半是上游搬来的子手册。

但真正决定手术方案的，是一组对比数字：

| 项 | 量 |
|---|---|
| 需要修的失效引用 | 13 处 |
| 如果要全树译成中文，待译正文 | 98.2 KB |

为修十三个 token 去译九十八 KB，是七千五百倍的代价。而且那份英文正文里，值得保留的东西恰好是它的操作细节：参数、检查项、命令。翻译它们等于把唯一权威做一次有损重写。

结论是：**不翻译，只换引用。** 读英文对模型不构成障碍，致病的是失效引用，不是语言。这一步是本篇里唯一一个“解剖决定手术”的地方 —— 先量，再决定切哪。

## 七、十四个文件都完整，模块图是断的

技能包里有一棵子树：`agents/gen-pptx/src/`，十四个 TypeScript 文件。

每个文件都以完整构造收尾，没有中途截断，语法上看不出问题。文件数也够。

它是**不可编译**的，证据链是这样：

- 六处模块说明符指向不存在的文件；
- 缺入口（没有 `cli.ts`，也没有 `index.ts`）；
- 缺构建产物 `dist/`；
- 整棵子树里没有任何 `package.json`、`tsconfig.json`、锁文件。

四个条件同时不满足，那就不是“可能能跑”，是确定不能跑。这棵子树是被砍掉的能力留下来的骨头 —— 它对应的能力（导出 PPTX）已经不在技能里了。

六个不存在的模块说明符里，有一个 `../types.ts` 被七处引用。这不是笔误，是整棵子树共同依赖的一个从未被写出来的文件。**当一个不存在的模块被多处引用时，问题不在引用处，在缺失处。** 顺着引用点一个个去修，会修出一堆局部补丁，而缺的那个文件始终没人补。

**判定“能不能跑”，不看文件数，看模块图闭不闭合、入口在不在、产物有没有。** 这一条在别的地方也救过我：功能看起来齐、目录看起来满，一跑就找不到模块，原因通常是最上游那个文件从来没被写出来。

同一个目录下的 `agents/gen-video/` 更干脆：零文件，只剩三个空目录骨架。事故残骸。

十四个文件里还带着压缩标识符的溯源标记（形如从 `dist/capture.iife.js` 反推得到的痕迹）。这说明它们不是随机损坏，是有意做的部分还原 —— 有人从构建产物往回抠了源码，抠到一半停了。

## 八、判据必须先能看见目标形态

这一节是整篇的手艺核心，也是我觉得最该被抄走的部分。

重构这个技能时，我立了三道关卡：技能合规校验、引用完整性、内容保全，每道都是现成脚本。我当时的验收写法是“关卡全绿”。

派发第四个任务之前，一个评审者把我的验收打回来了。他的发现是：**三道关卡都只读技能根目录下的 `SKILL.md`，没有一道读子树。**

而那个任务的主战场，恰恰是十五份子树文档里的十八处引用替换。“关卡全绿”这句话在那一刻是**不可证伪的** —— 它和“什么都没查”是同义的。如果按原样派下去，实施者做完，关卡照常绿，主战场可能一片断链。

于是我给这个任务补了一条子树专项扫描。跑起来第一件事就暴露了它自己的问题：它按技能根目录去解析相对路径，于是 `../apple/motion.md` 这种写法 —— 明明存在 —— 被判成 `[?]`。六十七个 token 里有六十三个进了“人工判读”名单，噪声把信号彻底淹了。

**我用来补判据盲区的那条命令，本身是坏的。**

重写成 node 脚本之后，我做了一件当时觉得多余、后来觉得必须做的事：给它做正控和负控。正控是拿 `built-in-skills/` 里四十六条链接跑一遍，报 0 条误报 —— 证明它不乱报警；负控是把同一份文件放到目标深度（`craft/artefacts/`），准确报出 2 条断链 —— 证明它真抓得住要找的东西。

我那时在会话里写过一句话，现在看还是这条纪律最准确的表述：**没有负控，我没法区分“真的没问题”和“脚本根本没在工作”。**

同一轮里还堆着几个同类发现，都是判据本身的毛病。下面四条是当时逐条记下来的：

一个是回归台账。关卡的内容保全检查按 token 计数，只要还有任何一处引用方存在，那个 token 就仍算“回归”。而重构是渐进式的：删掉的文件名，要等后面某个任务才轮到清。这意味着**关卡从第三个任务起就是红的，一直到第八个任务才转绿**。如果我按“关卡全绿”派下去，四个任务的实施者都会看到红灯，然后要么去改不该改的文件（撞车后面的任务），要么把真问题当噪声忽略掉。

另一个是 `pwsh` 不在本机。计划里有一处判据写成 `command -v pwsh` 应当是成功，实际上本机只有 Windows PowerShell 5.1 → 裸 `-File` 会被执行策略当场拒掉。

第三个是样例目录的名字。验收时要造一个最小设计系统当对照组，而设计系统的命名空间由那个目录名派生，并且被烧进三个产物文件里。所以那个目录一旦改名或者挪位置，逐字节比对会产出“全是差异”的噪声 —— 基线静默失效，但一步都不报错。

第四个更狠：引用完整性关卡的判据里有一条依赖 `git status`，而关卡脚本本身待在技能仓库之外。于是不管技能树怎么变，那个 `git status` 永远是干净的 —— **那道关卡在整轮重构里全程恒绿，它什么都没守住。** 这条是评审者读脚本读出来的，不是跑出来的。

把这几个叠在一起，判据失明就有六种形态 —— 前面各节出现过的那几种，加上这一轮新发现的。后果完全一致：**验收会绿，但绿的依据与你想验的东西无关。**

| 失明形态 | 现场 | 后果 |
|---|---|---|
| 读错对象 | 三道关卡只读 `SKILL.md`，而主战场在子树 | 验收不可证伪 |
| 没有负控 | 自写的子树扫描器按技能根解析，67 个 token 误报 63 个 | 噪声淹掉信号 |
| 无鉴别力 | 内容保全按 token 计数，渐进式重构期间必然报红 | 红灯被当噪声，或者动手改不该改的文件 |
| 前提不存在 | 判据写“`command -v pwsh` 应为成功”，本机只有 5.1 | 判据本身跑不起来 |
| 基线会漂 | `--freeze` 要求工作树等于基线，而任务一落地就永久偏离 | 唯一的绕过会静默重置判据 |
| 判的是别的东西 | 引用关卡依赖 `git status`，脚本却在工作仓之外 | 恒绿，零覆盖 |

到这里，那次重构里**被证明写错或不足的判据，超过了十五处**。没有一处是靠通读计划发现的，全部来自实施者的实测、评审者的独立复核，或者我自己动手预检。

这也解释了为什么这套流程看起来比“照计划做”慢得多。每一条被拦下来的判据，如果没拦，都会以一次**绿色的验收**放行一个真实的缺口。

## 九、手术只切了三刀

解剖的目的是决定切哪，不是决定切多少。这一轮只切了三刀。

**第一刀，冻结。** 技能里那五个 `.mjs` 脚本是整个包里唯一实测能跑的部分，纯 node 直跑，不装依赖。它们当黑盒：接口写进规格，内部一行不动。烂主要烂在文档层，那就只动文档层。这条纪律后来救了整轮 —— 管线是唯一不能出错的部分，而它恰好也是唯一不用改的部分。

**第二刀，砍转译层。** 三份宿主映射删掉两份，能力名到真实工具名的映射取消，文档里直接写本机真名。前面那些毛病 —— 下划线文件名、上游工具名、抬头不齐 —— 全部长在这一层上，砍掉它们一起消失。代价写进规格：以后想换宿主，工具名得重写。认了。

**第三刀，按类重分组。** 三十多份子能力原本按英文字母序排，没有分组。这才是“乱”的真正来源。重组成三块：制品形态与原型、设计系统、素材来源，砍掉的能力连同文件一起删。

还有一个不可逆点的处理值得一提：删除旧结构之前，先改名而不是直接删。`mv` 到带日期后缀的旧目录，新结构就位之后逐字节校验，最后再回收旧目录。任何一瞬间，磁盘上都有一份可用的技能。

## 十、补丁是有保质期的

技能里有三个文件带着同一行标记：`[LOCAL PATCH 2026-09-26]`。

这是本地改造的账。上游的脚本里用 emoji 当裁决标记，而这个工作区的约定是纯 ASCII 的 `[OK]` / `[FAIL]`，于是三处被就地改掉：构建预览脚本、设计系统检查脚本、检查器的代理提示词。

标记的作用是给未来留一个把手。上游一更新，这三处改动会被覆盖 —— 有标记，你知道升级后要重放三处；没标记，你得靠 diff 逐行看，而且看的时候不知道哪边才是“正确的”那一侧。

清理的时候我特意把这三份排除在清理范围之外，补丁原样保留。理由：它们不是待办事项，是已完成的本地化，动它们等于把上游的写法捞回来。

顺手记一条更普遍的纪律：**凡是“改了外部来的东西”，就该在改的地方留一行可检索的标记。** 标记要能被 grep 到，要带日期，要写清改了什么。这跟前面那些判据是同一条思路 —— 把只有你脑子里知道的事，搬到磁盘上。

## 十一、今天复查：好了的，和还欠着的

写这篇的时候我又把整棵技能树实测了一遍。用的是当初那套验收标准，逐条来。

好的部分：

| 判据 | 结果 |
|---|---|
| 规模 | 54 文件 / 4,068,953 B（重构前 89 / 4,196,602 B） |
| 入口 | `SKILL.md` 128 行 / 9,348 B |
| 入口引用的文件 | 30 处，全部在磁盘上（只有一处是刻意写的通配） |
| 子树孤儿文件 | `craft/` 与 `ds/` 共 18 份，零孤儿 |
| 上游工具名残留 | 零。`copy_starter_component`、`gen_pptx`、`super_inline_html`、`present_fs_item_for_download`、`open_for_print`、下划线版 `deck_stage.js` 全部无命中 |
| 字节卫生 | 0 个裸 NUL、0 个 CRLF、0 个 emoji |
| 死路 | `save-as-standalone-html.md` 现在指向本机真实脚本 `agents/inline-assets.mjs` |

上面最后一条值得多说一句。那个曾经依赖不存在的宿主接口、又拿另一处失效当兜底的能力，现在真能走通了：本轮为它新写了一个本地脚本，把 HTML 里直接引用的资源内联成单文件。

欠着的部分，我也照实列：

- **视觉终验没跑。** 新的视觉验证方式（交给本机的视觉 MCP 去读渲染结果）只有设计，没有实测记录。这是唯一一件登记在册的开口项，它不挡使用。
- **审计文档的口径没回写。** 三份文档里，规格头部还写着“状态：待复核”，计划的十个任务复选框**一个都没勾**，内部路径还全是旧机器的盘符。磁盘上的活早就干完了，文档没跟上。下一个零上下文的会话照文档读，会以为这活没开始。
- **可复现性缺口。** 验收时用的最小设计系统样例、基线文件、临时仓库，都在临时目录里，已经按约定清了；重构前那份八十九文件的原状备份目录，现在也是空的。也就是说“管线仍可跑”这条判据现在无法复跑，想复跑得重建样例；想回到重构前，本机已无副本。
- **六条冻结缺陷。** 管线内部还留着一批已登记、明确不修的东西：同一份磁盘格式有两套解析器、一个 manifest 字段只被消费不被生产、两个恒空字段、一行死码、一处恒真的守卫、一处用相对路径当权威指针。它们是**有记录地不修**，不是忘了。

还有一点我想单独强调。**“不修”和“没发现”是两件事，区别全在于有没有留记录。** 一份写着“这里已知有缺陷、本期接受、理由是 X”的清单，和一片没人看过的暗处，在磁盘上看起来是一样的，在下一个接手的人眼里是两回事。

## 十二、带走一份自查清单

把整篇的判据压成一张表。左边是症状，中间是你怎么机械地确认它，右边是动作。

| 症状 | 机械判据 | 动作 |
|---|---|---|
| 索引里的能力依赖本机没有的工具 | 抽出所有工具名，与磁盘和 PATH 对照 | 换成真名，或从索引里删掉 |
| 同一依赖出现两个相反判定 | 同一个名字 grep 全树，看结论是否一致 | 定一个裁决，改掉另一处 |
| 两份文档说法不同 | 两两比对，重合度 > 50% 即问题 | 合并，不要只加交叉引用 |
| 照着文档抄，第一步就失败 | 抽出所有反引号里的路径，逐个 `test -e` | 修文档或改名，别只修一处 |
| 某个大文件搜不到任何东西 | 字节级探针找 NUL，或 `rg --text` 对照 | 换成转义序列 |
| 目录很满但一跑就找不到模块 | 模块图 + 入口 + 构建产物三件套 | 判定不可编译，删掉或明确登记 |
| 验收写着“全绿” | 造一个必然违规的样本，看它报不报 | 判据没有负控，就不算判据 |

清单里那一行，才是这篇真正的结论。

一堆文件看起来齐、结构看起来清楚、脚本看起来能跑，都不能说明这个包是可用的。**结构的美和内容的可用是两件事。** 一个依赖单向无环、分层清晰的技能包，照样可以让你照着它的索引一路做下去，然后在最后一步收获一片安静的失败。

解剖的价值，就是把这些“看起来”变成一串能机械核对的条目。能被核对的烂，才有可能被修掉；报不出来的烂，只会一直待在那儿，等着下一个人照它做一遍。
