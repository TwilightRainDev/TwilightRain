> 我丢过去一句，编程用到的事实到处偏移，文件散落得到处都是，个个都说自己是权威来源，非常不好管理。我想把这些东西全部集中到一个目录，别处只留指针。
>
> 它把方向接了，把形状否了。
>
> 自动加载的那几层，做不成指针。

## 一、事实到处都是，个个都说自己是权威来源

先把病灶说清楚。

同一个事实会出现在好几个地方：技能里的参考文件写一份，记忆条目写一份，某个项目的说明文档再复述一份。每一份看起来都像权威，改的时候改哪份全凭记性，剩下的几份就成了沉默的旧版本。

举一个具体到可笑的例子：磁盘上有几块盘、每块是干什么的，这件事同时写在环境路由技能的事实表里、写在一条记忆里，还写在包根的说明文档里。三份都声称自己是最新的。

这就是当时的处境。我的判断是「散」，对策是「集中」。

## 二、我说全搬进一个目录，它说这个形状不成立

方案很直白：所有事实正文搬进一个目录，其他地方一律只留指针。一条事实只有一处可编辑的副本，其余位置写一句「见某某」。听上去无懈可击。

它回了一句：方向对，但这个形态不成立。

理由是**加载语义**。工作区里有几层东西是每个会话自动进上下文的，它们各自有各自的约束：

| 层 | 为什么做不成指针 |
|---|---|
| 记忆目录的索引 | 它天然就是「索引 + 指针」层，本来就长成你想要的样子 |
| 全局与项目说明文档 | 自动加载，正文必须自足——指针也占篇幅 |
| 技能层 | 技能必须自带内容，不能指向外面 |

最后一条推到底是一句很硬的话：**指针指不到的地方，就等于不存在。**

一个只会被「点开才生效」的指针，在自动加载的链路上等于零。所以「全部搬走、别处只留指针」这个形态，搬的恰恰是那几层不能只剩指针的地方。

它顺手把更根本的一句给出来了：

> 单纯搬家只是把漂移换个地址。

## 三、病根不在散，指标也不在文件数

挪完之后，它重新诊断了一遍：

> 真正的病根可能不是「散」，是「没有单一编辑点 + 没有漂移检测」。

前半句是位置问题，后半句是机制问题。「散」只是一个可观察的表象，把文件挪到一处，只是让表象消失，漂移该发生还是会发生。

接着指标也被换掉了：

> 集中化会增加指针数量，而每个指针都是一次失效机会。所以该盯的量是**同一个事实有几处可编辑的副本**，目标降到 1。至于是几个文件装着这些事实，随便，可以是 N。

这句话把整件事从「文件该放哪」换成了「这条事实有几支能改它的笔」。放哪是个整理动作，改它的笔有几支是个约束。

## 四、库长什么样

设计最后落在五样东西上。

**一、每条事实带四个字段**：`id`（标识）、`authority`（权威级别）、`load`（加载方式）、`verify`（验证方式），后面还长出第五个 `forbid`（禁止写法）。

其中最好用的是 `verify`——它装的是一条**可执行的命令**，用来验证这条事实是否还对。事实过期的时候，这条命令会自己变红，不用等人记得回来复查。

**二、一份索引**，写明「真值在此」，逐条登记。

**三、一份显式的排除清单**，列出哪些文档不算权威。这一步后来惹了麻烦，见第八节。

**四、一个检查器**。输入是整棵工作区，输出是漂移报告：哪条事实的 `verify` 红了、哪些文件被索引引用了但磁盘上没有。退出码 0 是干净，1 是有问题，2 是没跑出结论——**2 也是个正经结果**，表示「不知道」，而不是「没事」。

**五、标识提取规则**：`fact:([A-Za-z0-9_.\-]+)`。别的文档引用一条事实，不复制正文，写一个 `fact:` 开头的标识。检查器顺着标识去核对。

这五样凑齐之后，规矩就不再是「大家记得改一处」——它有了落点。

## 五、一份刚写完就被推翻的提案

库建成第二天，有个自我改进技能的提案工具例行扫盘，产出了一份提案：

「事实库停摆，需决定推进或关闭。」

它附了实测：

```
E:\WorkZone\ClaudeCode\fact\
├── .git\            (1 commit)
└── .gitattributes   (19 B: "* text=auto eol=lf")

find -> 除 .git 与 .gitattributes 外零文件
```

结论听起来很扎实：**仓库建好了，但一个事实文件都没有。**

我回了一句：事实库在改，你把提案 03 划了。

它复测了一遍，同一个路径：

| | 提案撰写时 | 复测时 |
|---|---|---|
| commit | 1 | 4 |
| 事实文件 | 0 | 19 条，含索引 |
| 域目录 | 无 | machine / workspace / credentials / network / model / tooling / projects / skills / github |

它自己写的教训是这样的：

> 本条从「实测成立」到「完全失效」不到一小时。

引号里是现象，现象底下那句才是要害：**提案有保鲜期**。当初的实测没有测错，是这条实测本身随时间失效了。

然后它没有删掉这份提案，只划掉留档。理由是删掉会让情节记录的溯源指向一个空洞——那正是同一个技能里另一条规矩要处理的问题。

一个工具产出「现状是 X」，X 在四十分钟后就过期了。这件事后来变成了整套文档纪律里最反复出现的一类。

## 六、一小时前写下的副本，现在是漂移

库建成之后，立刻浮出来一个新问题：同一事实出现了两处正文。而两处正文，按索引自己的定义就是漂移。

| 库里的正文 | 别处的副本 |
|---|---|
| `machine.drives` | 环境路由技能事实表的「开发工具链」「盘符」两行 |
| `machine.fs.delete-discipline` | 环境路由技能新增的「静默失效」整节 |
| `tooling.cli.adb` | 一条记忆 |
| `machine.git.install` | 环境路由技能事实表的 git 行 |

这份清单里最要命的是备注那一句：

> 其中 `EnvRouter` 那几行是**本次会话一小时前刚写进去的**——写的时候 `fact/` 还是空的，不算错；现在它是漂移。

同一段文字，一小时前是唯一副本，一小时后成了副本之一。**中间什么都没改，只是别处多了一个新的权威源。**

![](/img/360px/fact-store-one-copy-1.jpg)

这就是为什么指标要换成「有几处可编辑的副本」。它是唯一一个能随时间变化的量。

## 七、保护性写作，和一个 134 KB 的样本

库的事告一段落，下一个问题是文档。

我先给了个评价性的判断：最近的文档都在保护性编写，绕来绕去说今天改了什么、明天改了什么，真正失败的时候文档也没了，还会让模型注意力涣散。

它去找了个样本，一份 134 KB 的文档，占它所在那棵树全部体量的一半。那份文档开头自述：

> 本文件为增量写入产物，随调查推进逐节追加，中断后先前写好的章节仍然可用。

这就是原型。它的失败是双重的。

第一重：它把结论写成了工作日志。读到的人（和模型）得先把上下文重建一遍，才能取用里面的东西。

第二重更狠：它宣称的用途是「中断后仍然可用」，而它存在整个工作区里唯一没有版本历史的地方。声称能抗中断的东西，被放在最容易丢的地方。

还有一个更细的毛病，用相对时间定位事实：

> 用户**今天**仍在改活树。

写的时候很清楚。两天之后，「今天」的指称对象已经算不出来了。它管这叫**不可解析**——和噪声不是一回事，噪声可以忽略，不可解析没法忽略，因为读的人不知道自己读的是哪一天。

于是有了那条要求：

> 文档要自信，直接覆写对上磁盘。

不要「今天的现状」，不要「现状有误，应当是某某」。一份文档只描述它此刻所对的磁盘，对不上就改文档。改不动就说明文档不该存在。

## 八、同一条规矩写了三遍，没有一遍会失败

这条纪律当时存在于三个地方：项目说明文档的一节、自我改进技能里的一条模式、记忆里的一份文件。

三个地方，全是**陈述**。

它点破了症结：

> 三处都是陈述，没有一处在被违反时会失败。于是它描述的是偏好，不是约束。**再写第四遍不会改变任何事。**

这是全套文档治理里最值钱的一句，和我后来给钩子写的那篇是同一个道理：写在文档里的规矩，只在出事之后被想起来。

但这里要装一个会失败的检查，比钩子那边容易，因为零件都是现成的。检查器早就计算好了三样东西：全扫描面、自动加载层清单、索引的排除集。加一条 `narrative` 检查就行：

| 判据 | 级别 |
|---|---|
| 自动加载层出现相对时间词（今天 / 明天 / 最近 / 日前） | FAIL |
| 被自动加载层按路径引用，且在排除清单里登记为「非权威 / 允许白话」 | WARN |
| 事实正文里出现测量戳以外的绝对日期 | WARN |
| 被会话起点引用的文档里出现相对时间词 | WARN |

第二行是这里面唯一的新机制。它把「贴了非权威标签，又被会话起点链接」这个组合本身变成了可检出的病征。

因为当时正好撞上一个漏洞：排除清单给两份文档标了「导航（非权威）」，注明允许白话复述。而项目说明文档偏偏按路径指向这两份。于是「非权威」被实测成了「此处无需守规矩」，而且这个许可**恰好发给了离读取路径最近的两份文档**。

它对这件事的解释值得单独抄下来：

> 对模型而言这个标签的效果是不对称的：「非权威」降低的是**信任**，不是**成本**。token 照付，还要额外付一次「该不该信它」的判断。

所以「非权威」不该是叙事许可证。它只该意味着冷存储：不进扫描面、不被会话起点链接。

## 九、一次自我推翻，和例外的数量

同一份提案里还有一次自我推翻，它自己记在了文件末尾的更正里。

那份 134 KB 文档的姊妹篇，第 16 行有一句自标：

> 这是**当时的**恢复方向，不是落地结论。

提案一度把这句话当成正例，建议把「叙事自我标注为冷」升格成一条规则。

当天就被实测推翻了。理由是：**那段自标本身就是墓碑**——和它早先已经禁掉的一类东西完全同构，只是换了对象。给一段叙事加一句「这是旧的」，读者还是得读完整段才知道能跳过，成本一点没降。

正确的解法是搬家：把冷内容整个搬进冷存储。那天两份文档都被移进了历史目录，逐字节保真，前后 sha256 相同。

同一个会话里我还提了另一件事，让它去数例外：

> 再派一个子代理检查例外的泛滥性——1 个例外可能是好的，100 个例外就是坏的。

规则里的例外是有意义的，但它的价值和数量成反比。一条例外是一次「这次的规矩不算」，一百条例外等于没有规矩。

## 十、串行派本地模型，一篇一篇来

库和规矩都定完之后，该清存量了。

存量很大：整棵工作区六百多份 Markdown。用主会话去啃，光读就得烧掉大量词元。

我的要求是串行：

> 开始串行派发本地模型对工作区的 md 文档进行卫生处理，一次喂一篇，避免批量文档处理消耗大量词元。

于是派了十五次。全部跑本机那个 27B 的模型，上游词元消耗为零。

它做的事很清楚：扫描器直接 require 两道护栏本体的判定函数，**不复制词表**——复制词表就会跟护栏漂移，而护栏改了词表，扫描器还在按旧的判。扫描结果是一张带行列号的清单，逐条喂给本地模型去改。

其中一次很有趣。有个本地模型报回 BLOCKED，理由是：**提示词卫生护栏要求每次写入净减少**。它要做的替换是逐字等价的（`已合并而禁用` 改成 `合并后停用`），长度没降，护栏判它不合格，当场拦下。

解法不是绕过护栏，是把改动和目标词捆在一起改写一次——目标词加一句防御表述，一起换掉，净减少成立，放行。

终验的数字：

| | 开工前 | 终验 |
|---|---|---|
| 命中文件 | 604 篇里 17 篇 | 601 篇里 7 篇 |
| 命中处 | 31 | 16 |

剩下的 16 处全在我裁定保留的第三方正文里——六篇新闻和一篇转载。别人的文章不改。

## 十一、末态

这个库最完整的一次记录是 48 条事实、正文状态化、检查器管着，纪律生效。

今天我去核磁盘。

`E:\WorkZone\ClaudeCode\` 底下只有三个目录：`app`、`home`、`tools`。`tools\` 里只剩一个包内自带的 `git\`，那个回收站删除脚本、那个密钥读取脚本、那个检查器，都不在了。

全盘找索引文件，没有。找检查器主文件，没有。找任何一级名字里带 fact 的目录，没有。

但指针还在。技能里那句「本机 GitHub 事实的唯一编辑副本在 `fact\github\`」，今天照样写着。

那 22 条 `fact:` 开头的标识，最后一次成批出现，是在一份归档下来的记忆索引里。

整套设计里最想消灭的是一件事：**载体的状态和它对外的声称不一致。**

一个看起来像基础设施的空仓库，比没有仓库更糟——它读起来像「事实已经集中好了」，实际是零。

指针指向空处，是同一件事的另一个版本：**只要没人去点它，一个指向空处的指针读起来和一条真事实没有区别。**
