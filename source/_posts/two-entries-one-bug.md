> 我丢过去一句，帮我把 `E:\LLM\Qwen-Image-2.1` 的工作流搭一下，生一张参考图库里那种画，差异点是橙色女孩趴着身子，而不是躺着。
>
> 那台机器上只有一个画图模型、三个权重文件、一块 8 GB 显存。
>
> 接下来发生的事，基本上是一个报错接一个报错。

## 一、先交代台架

环境是自包含的一份 ComfyUI，整个目录自成一体。Python 3.14，PyTorch 走 cu130，显卡是那块 8 GB 的 RTX 5060 Laptop，服务挂在 `8188`，启动参数里带着 `--reserve-vram 1.2`，另有启停两个脚本。

权重只有三个：一个扩散主干、一个文本编码器、一个 VAE。加起来 10 GB 出头，塞进 8 GB 显存，靠的是 NVFP4 量化和把缓存挪到 CPU。

要干的事听着很简单：给一张参考图，改一个属性，别的都不动。

## 二、扁平键、点号键

第一版图生图是命令行提交的。报文写完，提交成功，排队成功，然后执行时报错：

```
TypeError: unexpected keyword argument 'image_1'
```

这个节点的参考图输入是个会自动扩展的槽位，名字从 `image_1` 排到 `image_16`。而在 API 报文里，键必须写成带点的路径：

```
"images.image_1": ["9", 0]
```

扁平写法能过提交校验，死在执行阶段。根因在读得到的那几行源码里：那一层用点号把前缀和槽位名拼起来，所以在它眼里 `images.image_1` 和 `image_1` 是两个不同的东西，前者能对上前缀，后者对不上。

改完，命令行通过。

## 三、同一个报错，从界面回来

然后我贴了一份界面上的报错过来，问这是怎么了。**一模一样的 `TypeError`，一模一样的 `image_1`。**

这次的原因不在代码里。工作流存成 JSON 之后，那个槽位是这么一行：

```
{ "localized_name": "image_1", "name": "image_1", "shape": 7, "type": "IMAGE", "link": 11 }
```

前端把保存下来的名字**原样发出去**。凡是以前存过这个工作流的文件，槽位名都还是扁平的。于是同一条命令、同一个节点、同一个根因，从完全不同的入口进来第二次。

修法是把所有工作流文件里的槽位改成带点的那个名字，而且**改两处目录**——启动脚本会把工作流目录整体复制到用户目录一次，两边都得改。另外还得告诉操作的人：重新打开工作流，别先运行或保存内存里那份旧图，否则旧的扁平名字又写回去了。

**同一个缺陷有两条入口。修完代码路径不等于修完。** 第二条入口是磁盘上那些已经存下来的文件，它们不会自己更新。

## 四、那个分辨率不是边长

同一个节点上还有第二个名字骗人的参数。

它叫「分辨率」，默认 1024。看到这名字会以为画布是一千零二十四见方。实际上它是一个**面积预算**：给一张 1448 乘 1086 的源图，填 1024 出来的是 1184 乘 896；填 1536 出来的是 1760 乘 1344。比例跟着源图走，总像素数贴着那个预算。

填 0 又是另一种意思：保持每张参考图各自的尺寸，只做 32 的整数对齐。

想知道代价的时候，这两个数比名字有用得多。同样那张源图，1024 大约是每步 1.19 秒、采样三十秒上下、整条提示跑完 44.9 秒；1536 涨到每步 4.2 秒、整条 139 到 141 秒。**8 GB 显存下两种都能跑完**，代价只体现在时间上。

## 五、一条 125 个节点的社区工作流

中间我拿了一份社区重绘工作流，一百多个节点，一百六十多条链接，几十种节点类型。要求是开无头浏览器，看看它能不能用。

先做静态检查：全量问一遍服务器有哪些节点类型，再逐个比对。第一次的结论是「所需的节点类型全都在」。

这个结论是错的，而且错得很难看。

因为查单个未知类型时，那个接口返回的是 **200 加一个空响应体**。我看的是状态码，状态码说没问题，于是三十九种类型全判成了存在。换成拉全量表（九百七十种）重比，**十二种类型确实缺失**，另外十三个引用的模型文件也一个都没有。

静态说不可用，再从真实前端走一遍确认：在无头浏览器里加载、转换、提交、点运行。结果是四个节点转换出来 `class_type` 是空的，服务器返回缺节点类型，点击运行**排队零个任务**。

两轮独立证据一致。判定不可用，弃掉这个方案。

那天还有一条附带发现：界面提示某个扩展管理器需要升级才能装缺失节点。也就是说这条路不是「缺几个文件补上」，是整条依赖链在这个自包含环境里没打通。

探测那头也有它自己的纪律。无头浏览器这种东西容易在机器上留下残骸，所以每轮都带一套不变式：一个唯一标识写进独占的用户数据目录；启动参数带 `--no-sandbox`；关停顺序是先优雅退出、再轮询、再按标识重扫一遍、再按进程号精准终止、最后断言残留为零；**绝不按进程名杀**。只有在干净关停的前提下才删那个配置目录。

这套东西第一次用就派上了用场。某轮探测报告里提交标识是空的，看上去像「点了运行没反应」。改去查服务器的队列，发现任务**确实排上了**，节点数和参考图槽位都对。结论是探测器没听到，不是没发生——前端换了提交走的路由，探测器的监听还挂在旧的那条上。

**一个空白的探测结果，可以是探测器的问题，不是被测对象的问题。** 这和前面那个「200 加空响应体」是同一类东西：一个查不到东西的查询，回答的是「没问题」。

## 六、参考图驱动的局部重绘

弃掉社区方案之后，回到自己搭。

目标是：给目标图加三到七张参考图，只重画一个局部，其余像素不许动。

拆开是四件事。

**参考图槽位**：那个节点本身支持最多十六张，按序号排。

**空槽位**：没接图的槽位可以不删，标记成静音就行。静音节点在界面转 API 的时候被丢掉，节点收到的是空值、直接跳过。**不报错，也不引起序号错位**——这一点很关键，否则每加一张参考图都要重排一遍链接。

**遮罩**：这个环境里加载图片节点输出的遮罩，算法是 `1 - alpha`。也就是说**遮罩必须画在 alpha 通道里**。拿一张黑白 PNG 去当遮罩，得到的是全零，也就是哪里都不改——它会安静地什么都不做。

**合成**：先用一个膨胀节点把遮罩撑大一圈做羽化，再用合成节点按遮罩贴回去。遮罩外的地方是原图原样，一张像素都不差。

然后把这几件事串起来跑通。

## 七、遮罩不能放在目标图的 alpha 里

第一版的设计里，遮罩就画在目标图自己的 alpha 通道上。这个方案在开工前就被拦下来了。

理由是：这个节点保留四通道，而只有视觉塔会把 alpha 合成到白底上。**如果遮罩画在目标图的 alpha 上，模型看到的那块区域就是透明的。** 它看到的不是「这里要重画」，是「这里什么都没有」。

所以遮罩必须来自一个单独的图片节点，那个节点的图像输出根本不用，只取它的遮罩输出。

这种坑的形状值得记一笔：**一个字段同时有两个可能的读者**（模型和合成器），而它们对同一个字段的理解不一样。给其中一个看的标记，会被另一个当成内容。

## 八、序号指代不可靠

工作流能跑之后，我在界面上让它按第二张参考图重画，出来的是第三张的风格。

做了一组对照：要求指定第三张，出来的还是那一张。

**按序号指代参考图，靠不住。**

换成在提示词里**用文字描述那张参考图**，同一套槽位、同一个种子，出来的是要的那张。于是默认提示词被整个改写成描述优先：不写「用图 2 的头饰」，写「用图 2 里那个黑蕾丝、深红玫瑰的头饰」。

这件事的代价很低（多打几个字），收益是确定的。

## 九、文生图，和唯一的一种画布

搭完图生图，接着搭文生图。

环境自带的说明里点名了一个文生图工作流，但盘上没有这个文件。按说明里的参数重建了一份：分辨率 1024、25 步、CFG 1、欧拉采样加 simple 调度器，前缀缓存用 auto 加 int8。

重建的过程中撞到一条硬约束：**文生图只有方画布。** 通用的空 latent 节点在这里一个都对不上——这个模型的 latent 是 64 通道、16 倍压缩，形状完全不是通用节点给的那个。所以没有参考图的时候，画布就是那个边长乘自己。**想要非方形，只能喂一张参考图，让它照着推比例。**

## 十、把官方件下下来比对

工作流交付之后，我下了一份官方的工作流过来，说我们比对一下。

逐字段比完：拓扑、节点参数、连线全部一致——**我按说明重建的那份，一个参数都没漏。** 不同的只有三处：示例提示词、种子是固定还是随机、存盘文件名前缀。另外我多放了一个备注节点。

确认完之后问怎么收口，我选了删除官方件，保留我这份的设置。

顺带在盘上看到一条会咬人的机制：那个启动脚本是**无条件**把工作流目录整个复制过去的，每启动一次覆盖一次。当时两边已经有三个同名文件内容不一样了——也就是说，在界面里改工作流并保存，下次启动会丢。要留存，得往工作流目录里存一份。

这一路里最值钱的三个发现，全都不在代码里。

一个是**同一个缺陷可以从两个入口进来**，第二个入口是磁盘上存下来的旧文件。一个是**同一个字段可以被两个读者用两种方式理解**，于是给一个看的标记会变成给另一个看的内容。还有一个是**空白结果不算结论**——查不到的那个查询回了成功，没听到的那个探测器回了空，两次都差点被当成「没问题」。

这三条的共同点是：它们都不抛异常。
