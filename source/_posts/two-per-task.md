> 我丢过去一句，你负责 texttool，目前有说法是不要做，因为会改契约，请你去除这些声称，我们要开始版本大更新了，必须要一个没有问题的交付版本。
>
> texttool 是我自己写的一个中文文本检查器。
>
> 于是接下来这几天，这个仓库里跑的不是一个人，是一队人。

## 一、起手是一句「不要做」

这个工具是我自己用的，干的事很具体：拿一份中文文本，把有问题的位置连着行列号报出来。规则分三组——标点字符类的、词汇类的、句式类的，另有一组统计观察，只出现在报告末尾，不参与判定。

它有一套对外的输出契约，机器读的那种。

「不要去改契约」是一种很稳的保守：契约一动，下游全断。但保守攒久了也是一种债，攒到某一天你会发现所有改动都在绕着一个已经不太对的东西走。

我的要求很直白：去掉这些声称，出一个能交付的版本。

## 二、它其实是从一份技能备份里迁出来的

这件事的起点不在这个工具。

我先是让它去比一份技能备份和现役那份技能的差异。那份备份里装的是一套去 AI 味的方法论，写在提示词里的。比完之后我说了句想法：这套东西可以给文本工具直接做一个新模块，把备份里的做法迁进来。它评了一遍，我觉得可行，然后才说，开始写计划吧。

这条路径值得记一笔：**同一套规则，写在提示词里和写在代码里，是两件事。**

写在提示词里，它靠模型每次读一遍然后自觉执行；迁进代码，它变成一条跑完会给你退出码的检查。前者是建议，后者是判定。

## 三、每个任务配两个人

拆成十二个任务。每个任务两个人：一个实施者动手，一个评审者挑刺。评审过了之后再复评一轮。

实施者交回来的东西长这样：

> 全量测试 259 通过、0 失败、0 跳过；构建 0 警告 0 错误；格式检查退出码 0；两文件实测行尾无回车、无 BOM。

评审者交回来的东西是带文件行号的清单，分三档：Critical、Important、Minor。一段典型结论是「规范合规，Critical 0 条、Important 0 条、Minor 6 条」，后面跟着那六条的逐条摘要——其中一条是「这段代码的右边界分支从来没被执行过」，还附了能判死它的补测用例。

评审报告里还有一类条目很值得留着：**无法从 diff 验证的事项**。比如提交信息里的署名、测试到底跑没跑。评审者不假装自己看见了，而是把这些单独列一档，指明该由谁自证。一份什么都敢下结论的评审，可信度反而更低。

测试计数一路往上：257、259、264、266、274、275、293。

这套流程里最值钱的不是这个数字。是**评审者报出来的东西真的会拦人**——Important 那一档不解决完，任务不算完。

## 四、动手之前先报冲突

最好的一条发生在某个实施者动手之前。

他没写代码。他先停下来了，报了一个 brief 里的自相矛盾：brief 只说了追加两个测试，但**既有的**那个测试是拿一个大小写变体当非法值用的；而这一步的改动正是把校验改成大小写不敏感——改完那个值就合法了，那个既有测试必挂。

他给了两个方案，说了自己倾向哪个，然后等人拍板。顺带把证据也带上了：全量跑一遍，除了这一条，零连带损伤。

这个动作值得单独说：**他既没有替我做决定，也没有闷头照着 brief 走。** 前者越权，后者是套模板。他做的是把「这份 brief 有洞」这件事，在代价发生之前摆到台面上。

## 五、契约升到 v2，转义面有七行

契约里最琐碎、也最容易错的是转义面。

实测下来，要转义的可打印 ASCII 一共七个：双引号、和号、单引号、加号、小于号、大于号、反引号。反斜杠走双反斜杠，不走十六进制。中文和一串常见符号都不转义。

这里还有一个只有肉眼比对才会遇到的问题：**两套转义来源的大小写不一致。** JSON 编码器出大写形式，隐形字符那套出小写形式。都是合法的转义序列，解析方解回来是同一个字符——但如果你拿文本去 diff，会以为两边不一致。

同一批改动里还把行尾统一成 LF，命中按行列排序。

## 六、跑一遍只收一格

这个工具除了检查，还有一半是替换：按一份方案表做确定性的字符归一化——隐形字符清掉、点号串统一、重复标点折叠、全角字母数字转半角。

方案表是数据，装在可执行文件所在的那个目录里。程序从**它自己的位置**读，不从当前工作目录读，也不从技能目录读。所以技能侧那份改完之后，得有一条安装动作把它并过去：同名覆盖，其余保留。这次只改了方案的自述文字，一百零八条规则一条没动。

而自述里最该写清楚的，是那条别扭的行为：**重复标点折叠，一遍只收一格。**

连续三个句号，跑一遍变成两个；跑第二遍才变成一个。它永远不会变成省略号——省略号那条规则管的是 ASCII 点号串，跟这个不是同一条。跑多少遍都到不了。

所以这条的验证不能只看「跑过了」，得看单次行为：拿一段带跨标点混乱组合的样例跑一遍，看它到底折叠成了什么。

## 七、段落口径是个自动判定的东西

这个工具报位置的时候要分「段」，因为有几条规则是按段生效的。而什么算一段，得先判一次。

判据是取全文头 4096 个字符，数空行：空行占比够高、且空行数少于总行数，就按 Markdown 口径切段（空行分段、软换行并进同一段）；否则按行式口径，每个非空行各自成段。

后来补了一条边界：**空文本和纯空白文本判行式。**

而这个判定必须跟着报告一起输出。原因是同一个文件用两种口径扫，命中数不一样——不说明用的是哪种，那份报告就没法复核。

## 八、有人断言本机没有 Python

这一路最像样的一处错误。

一个实施者做开工前侦察，报回来一条阻塞点：**本机没有 Python。** 他跑了命令探测，拿到的是应用商店的占位程序；另一个常见的启动器也不存在。于是他下了全称结论，还附了绕开它的替代路径。

几分钟后他自己纠正了：全路径那个解释器是好的，3.14.7，退出码 0。

而磁盘上有一条事实**逐字写着这个坑**：那个占位程序不带解释器，别把它读成这个结论。那条事实还要求一律写全路径。

他自己的复盘只说了一句：根因是没先查索引，把一个占位程序的行为当成了环境事实。

这个错误的形状值得单独记下来：**占位程序在命令和解释器之间插了一层。命令存在，解释器不存在。** 「有没有这个命令」得到的答案是真的，从它推出来的结论是假的。

这类错误不报错，它只让人绕远路。

## 九、三处裸 python

同一个坑的余波还在别处。

技能文档里有三处写着裸命令。照抄那条命令，在本机上必定失败——它落在占位程序上。

三处改成全路径，收口。文档锚点跟着重算：201 行，文件大小从 14613 字节走到 14657，再走到 14679。每改一次，那条验证命令手工重跑一遍，确认它还对得上磁盘。

锚点之所以要跟着改，是因为那条验证命令本身就是一条断言：文件大小对不上，它就自己变红。

## 十、终审：一个错数字差点进标签

终审的判定是「需修复后合并」：Critical 零条，Important 一条。

那一条是这样的：README 里写某个规则在一份示例文本上命中 4 处，而**出货的二进制实测是 2 处**。同一句里另一半是正确的——换成全角括号那版确实是 0 处。

两行文本，零代码风险。但它必须在打标签之前改，否则这个错数字会进那个版本的标签内容里。

改完复核：半角那版 2 处、退出码 1；全角那版 0 处、退出码 0。

另有一处同类的：文档里写「与远端比对的计数期望是 0 0」，实测是 `0 22`。原因是那行命令是在一个还没有合并的分支上跑的——**命令没错，前提没写。**

## 十一、留到下一轮的那些

终审把三十一条 Minor 逐条分诊，其中三条判为合并前必修，其余留到下一轮。

我当时问了一句：

> 终审分诊为「留到下一轮」的弱断言，还有留着下一轮的东西吗。

这句话问的不是那三十一条。问的是**分诊这个动作本身有没有被审过**。把哪些东西划到「下一轮」，是一次判断，不是一次观测；而判断是会被写得漂亮的理由说服的。

## 十二、末态

版本打到 3.0.0。测试从 257 条涨到 293 条。标签从十三个变成十四个。

最后一句我问的是：

> 开始推送，开始最后一次确认，真的没有待办和技术债了吗。

确认完，归档。

这一版交付下来，最让我踏实的不是那 293 个测试。

是那几条**在动作之前就被摆到台面上的冲突**——一个必挂的既有测试、一个会进标签的错数字、一条不成立的简写命令。它们本来都会安静地过去，然后在更贵的地方现形。

而这套流程里最像样的那处错误，恰好是由一个 Agent 自己发现、自己纠正的：它把一个占位程序的行为读成了环境事实。**流程能拦住别人，拦不住你对世界的误解**——那个只能靠先查一遍。
