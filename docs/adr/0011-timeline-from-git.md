# ADR-0011：时间线改为构建期解析 git 日志

## 状态

已实施（2026-09-25）

## 背景

`/timeline/` 的 7 条事件是手写 front matter，末条停在 **2026-08-17**。
此后五周内仓库有 8 次以上提交、5 篇新文、两轮语法收敛，一条都没登记。
手写台账在这种更新频率下已被证明不可维护——不是「暂时没更新」，是没有机制强制更新。

2026-08-25 上一轮的结论是「有真实数据，保留展柜页」，本轮由上述实测推翻其维护假设。

## 决策

事件改由构建期解析 `git log` 生成。

口径（拍板）：**除维护类前缀（`docs` / `chore` / `style` / `test`）之外全部算事件**。
不用「`feat:` 才算」：本轮最大的功能变化之一「提示块语法收敛为 `:::admon[...]`」的提交类型是
`refactor(admon)`，按 feat 白名单会漏掉。放宽后仍滤掉 docs/chore/style/test 噪音。

## 后果

- 时间线随每次构建自动更新，不再依赖人工登记
- 事件措辞是开发视角（提交信息写给开发者），与访客视角存在错位；这是自动化的固有代价。
  实测该口径在 HEAD `226084ad` 上产出 **130 条**事件、集中在 **21 天**（单日最多 23 条），
  故渲染层加同日分组，顶层压到 21 条；单日多条的详细项以 `.timeline-subitems` 子列表呈现
- **口径注记：计数与 HEAD 绑定，不是固定值。** 事件数、跨天数、顶层条目数都随提交单调增长，
  即便用的是同一个 HEAD。本 ADR 写下时（HEAD `226084ad`）实测 130 条事件 / 21 条顶层，
  而线上实际已是 **22 条顶层**——差值恰是本轮自己的三个非维护类提交（2026-09-25 成为一个新日期）。
  故任何「N 个提交 → M 条事件」的绝对数字复验都会得到不同结果；
  **验收只锚定提交与渲染形态（同日分组生效、单日多条走 `.timeline-subitems` 子列表），不用绝对数字**
- `renderPageTimeline` 因此新增同日分组行为。单日单条的输出逐字节不变，兜底快照的渲染结果零变化
- 数据源依赖构建环境有完整 git 历史。要求是 HEAD 处能追到现有时间线起点（2026-07-30）之前：
  本 ADR 写下时仓库有 168 个提交、最早 2026-07-21。**提交数随开发增长，此处不构成判据**；
  浅克隆的判别见 [WORKFLOW.md → 发布与验证](../WORKFLOW.md#发布与验证)
- 兜底：浅克隆或无 git 时回退到 front matter 的手写快照，页面不会变空
- 构建命令需保证完整历史：**不要**直接写裸的 `git fetch --unshallow && npm run build`
  （完整仓库上 `--unshallow` 退出 128，`&&` 会吃掉构建），用带浅克隆判据的写法，
  见 [WORKFLOW.md → 发布与验证](../WORKFLOW.md#发布与验证)
