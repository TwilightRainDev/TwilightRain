# 原图/360px 双轨图片 实施计划

> **对于执行者：** 使用 ExecutingPlans（或 SubagentDrivenDev）逐任务实施。步骤用 `- [ ]` 跟踪。
> 设计依据：`docs/specs/2026-08-21-img-ori-360px-design.md`

**目标：** 访客默认只加载 360×360 展示图；原图仅通过 fancybox「查看原图」打开；仓库只跟踪 ori，360px 构建生成。

**架构：** `sharp` 从 `source/img/ori` 生成 `source/img/360px`（gitignore）；Hexo 构建前兜底生成；模板与正文引用 360px + `data-ori`；fancybox 3 自定义按钮打开 ori。

**技术栈：** Hexo 8、Node ≥20.19、sharp、fancybox 3.5.7、既有 ink 主题

## 问题陈述

首页与文章图片按接近原图体积加载，叠加 canvas 全图像素取色，导致卡顿。

## 解决方案

双轨存储：ori 入库；360px 构建产物；UI 只展示小图；灯箱提供查看原图。

## 用户故事

1. 作为访客，打开首页时只下载小图，滚动更顺。
2. 作为访客，点正文/头图进入灯箱后，仍看到清晰够用的 360 图。
3. 作为访客，在灯箱左上角点「查看原图」，新标签打开完整原图。
4. 作为维护者，只需把原图放进 `source/img/ori/`，跑构建即可得到小图。
5. 作为维护者，git 历史不会因反复生成小图而膨胀。

## 全局约束

- 360px：居中 cover 裁切 360×360
- `source/img/360px/` 必须在 `.gitignore`
- `icon.svg` 与主题 cursors 不进双轨
- Cloudflare Pages 只认 `main` 构建；`npm run build` 必须能无预生成缓存地产出 360px
- 未经用户明确要求不 `git commit` / 不推送
- 行尾 LF

## 文件结构（职责）

| 路径 | 职责 |
|------|------|
| `scripts/gen-thumbs.js` | 扫描 ori→写 360px；可 CLI / 可被 filter require |
| `scripts/img-thumbs.js` | Hexo `before_generate` 调用 gen-thumbs |

| `.gitignore` | 忽略 `source/img/360px/` |

| `themes/ink/layout/index.ejs` 等 | cover/缩略图走 360px |

| `source/_posts/*`、`gallery`、`links`、`hello-world` | 路径迁到 `/img/360px/...` 或 `/img/ori` 仅用于 og |

## 决策文档

- 只用两档：ori + 360px；灯箱内也是 360，不另做中图。
- 生成库选 **sharp**（生态成熟、CF Pages/Node20 可用）。
- JPEG quality 82 + mozjpeg；PNG 保持 PNG。
- 路径镜像相对 `ori/` 根，不使用 `_ori` / `_360px` 文件名后缀（文件夹即语义）。
- 社交图用 ori。
- 取色降采样为性能附带修复，属本功能范围。

## 测试决策

- 本仓库无前端单测框架；以构建产物存在性 + 本地 server 手工回归为主。
- 回归点：首页卡片、文章头图灯箱、正文图灯箱、gallery、links 头像、hello-world cover、关闭灯箱后头图不消失（既有 afterClose 修复）。

## 范围之外

- Git LFS、外部图床、WebP 全站替换、fancybox 升级到 v4、自动从剪贴板传图。
